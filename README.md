# Maru (가칭) — 웹 우선 3D 강체 물리엔진

설계 정본: `../physics-engine-design/02-architecture.md` (v0.21, GPT 교차검수 23태스크 approve).

## 상태: M2 (강체 동역학 — 솔버·조인트·슬리핑·스냅샷)

| 크레이트 | 내용 |
|---|---|
| `maru-math` | 스칼라 `Vec3`/`Quat`/`Mat3` + `Vec3x4`/`Aabbx4`(SoA 4-wide, 핫패스 정본 — 설계 §3) |
| `maru-collide` | 셰이프(convex radius) · 듀얼 4-ary 트리 브로드페이즈(트리 비의존 canonical 페어) · GJK/EPA · 클리핑 매니폴드(feature ID) |
| `maru-dynamics` | TGS-soft 솔버 · PCM warm-start · 아일랜드/슬리핑 · point·hinge 조인트 · 캐노니컬 스냅샷/L0 리플레이 해시 |
| `maru-bench` | 마이크로벤치 + 피라미드 스택 벤치. native/wasm 동일 소스, 체크섬=결정론 스모크 |

### 측정된 스택 안정 봉투 (2026-07-26 **장기창 + 서브스텝** 재측정, native release, 50초)

`cargo run --release -p maru-bench --bin pyramid100 -- <substeps> <steps> <tiers>`

**창 길이도, 서브스텝도 기준의 일부다.** 이전 표는 600스텝(10초)·4서브스텝 기준이었고
40단을 "안정"으로 적었다. 3000스텝(50초)으로 늘리면 40단은 1200스텝 부근에 붕괴한다.
그리고 봉투를 실제로 묶고 있던 것은 **서브스텝**이었다(hertz가 아니라).

| substeps | 안정 상한 | 비고 |
|---|---|---|
| 4 | **29단** | 30단부터 붕괴 |
| **8** (기본) | **60단** | 60~63 구간은 비단조(61 붕괴·62 안정), 80단 붕괴 |

**서브스텝을 8로 올리면 더 안정적이면서 더 빠르다.** 40단 기준 8 ms/step(붕괴) →
2 ms/step(안정). 서브스텝 2배 비용이 **수면으로 인한 절감에 완전히 묻히기** 때문이다 —
정착한 스택은 비용이 0에 수렴하고(브로드페이즈 캐시), 못 자는 스택은 영원히 전부 계산한다.
대가는 **정착하지 않는 장면**에서 2배 비용이 그대로 남는 것이다(구 더미 참조).

**이 엔진에서 장기 안정과 수면은 같은 사건이다.** 잔류 속도가 임계 아래로 떨어지면
아일랜드가 얼어 영구 안정이 되고, 아니면 지터가 높이에 비례해 자라 붕괴한다
(30단 실측: t0 0.003 → t29 0.792 m/s, 시간에 따라 지수 증가).

### 외부 엔진 대조 (rapier3d 0.34, 동일 장면·프로파일, min-of-3)

`cargo run --release --manifest-path compare/Cargo.toml -- all 200 80 3`

| 장면 | Maru | Rapier | 비고 |
|---|---|---|---|
| **피라미드 10단** | **0.032 ms** | 0.042 ms | **24% 빠름** |
| **피라미드 20단** | **0.128 ms** | 0.170 ms | **25% 빠름** |
| **피라미드 30단** | **0.295 ms** | 0.494 ms | **40% 빠름** |
| **피라미드 40단** | **0.512 ms** | 1.058 ms | **52% 빠름** |
| 구 더미 500 | 3.54 ms | 0.233 ms | 15× 느림 — **정착하지 않는 장면** |
| 구 더미 3000 | 27.3 ms | 2.15 ms | 13× 느림 |

**정착하는 장면에서는 앞서고, 정착하지 않는 장면에서는 크게 뒤진다.**
격차의 정체는 대부분 "잠드느냐"다: 브로드페이즈 캐시(아래)로 전원 수면 구간은
동률이 됐다(10단 0.062 → 0.041 ms, 브로드페이즈 22 → 2µs). 30단 이상에서 벌어지는
격차는 Rapier가 잠들어 비용이 0에 수렴하는 반면 Maru는 잔류 지터로 **한 번도 잠들지
못하기** 때문이다(bp 재사용 0/200). 즉 **솔버 수렴이 안정성·성능의 공통 병목**이다.

브로드페이즈 캐시: 설계 §4.1이 "페어 집합은 **트리 비의존**"을 계약으로 두었으므로,
입력(자세·sweep·생존 집합)이 그대로면 재계산 결과가 비트 동일하다 — 재사용은 근사가
아니라 **항등**이다. 적분된 바디가 하나도 없는 스텝은 트리를 다시 짓지 않는다.

## API 계약 (M3 바인딩이 고정할 것)

- **`pose.pos`는 질량중심이다.** hull은 생성 경계에서 질량중심으로 재중심화되므로 엔진이
  보고하는 자세가 호스트가 준 원점과 다를 수 있다. 호스트는 원래 정점 버퍼를
  `pose.pos + pose.rot * body.shape_origin_offset()`에 그린다.
- **쓰기는 커맨드 큐가 정본**이다. `enqueue`는 **큐에 넣는 시점에 검증**하고 실패하면
  `ApiError`를 돌려준다 — 큐에 들어간 커맨드는 항상 구조적으로 유효하므로 자기 월드가
  만든 스냅샷은 항상 자기에게 복원된다. enqueue 이후 앞선 커맨드가 대상을 지우면
  flush에서 거부되어 리포트에 잡힌다(스텝은 중단되지 않는다).
- `enqueue_add_body`는 슬롯을 예약하고 **핸들을 즉시 반환**한다. 예약 슬롯은 쿼리에
  보이지 않지만(아직 alive 아님) 같은 배치의 후속 커맨드에 쓸 수 있다.
- 불변식 보유 필드는 전부 비공개다. 읽기는 게터, 쓰기는 검증하는 API로만.
- **`dt` 계약: `MIN_DT(1e-4) <= dt <= MAX_DT(0.25)`.** 0과 음수는 합법이 아니다 —
  일시정지는 step을 부르지 않는 것으로 표현한다("성공했는데 아무 일도 없음"이 오류와
  구분되지 않으면 호스트가 정지 원인을 진단할 수 없다). 하한이 있는 이유는 soft 계수의
  `1/h`가 폭발해 조인트 bias가 중간 연산에서 f32를 위협하기 때문이다. 고정틱 엔진이므로 큰 dt를 쪼개는 것은
  **호스트(accumulator) 책임**이다 — 탭 복귀처럼 큰 dt가 오면 여러 스텝으로 나누거나
  프레임을 버린다. 엔진이 조용히 클램프하면 시뮬레이션이 실시간과 어긋난 채 진행돼 더 나쁘다.
  위반은 trap이 아니라 `try_step`의 `ApiError`로 표현된다.
- **실패는 오류로, trap으로가 아니다.** M3 바인딩이 쓰는 정본 경로는 전부 fallible이다:
  `World::try_new` · `try_set_params` · `try_step` · `try_snapshot` · `try_state_hash` ·
  `Body::try_new_dynamic`/`try_new_static`/`try_new_kinematic` ·
  `Joint::try_point`/`try_hinge` · `World::try_add_joint` · `enqueue`.
  같은 이름의 비-try 함수는 패닉하는 편의 래퍼(테스트·진단용).
  `Joint::try_hinge`가 따로 필요한 이유: 0/NaN 축은 **Joint 생성 시점**에 걸리므로
  `try_add_joint`(이미 만들어진 Joint를 받는다)로는 잡을 수 없다.
- **지원 범위는 차원별**이다(`maru-collide/limits.rs`). 스칼라 하나로 묶으면 동시에
  너무 넓고 너무 좁다 — 넓으면 큰 위치 × 작은 역질량이 조인트 솔버의 **중간 연산**에서
  먼저 Inf가 되고, 좁으면 정상 물리의 임펄스가 잘려 warm start가 조용히 부족해진다.

  | 차원 | 범위 | 위반 시 |
  |---|---|---|
  | 셰이프 치수 | `MIN_SHAPE_EXTENT` 1e-3 ~ `MAX_SHAPE_EXTENT` 1e3 m | 거부 |
  | 위치·파라미터 (월드 범위) | `MAX_INPUT` 1e4 m | 거부 |
  | 조인트 앵커 (레버암) | `MAX_ANCHOR` = 셰이프 범위 | 거부 |
  | 선속도 | `MAX_SPEED` 1e4 m/s | 거부 |
  | 각속도 | `MAX_ANGULAR` 1e2 rad/s | 거부 |
  | 질량 | 1e-6 ~ 1e6 kg | 거부 |
  | 역관성 | 1e-10 ~ 1e12 | 거부 |
  | dt | `MIN_DT` 1e-4 ~ `MAX_DT` 0.25 s | 거부 |
  | 조인트 앵커 (바디별) | 그 바디 바운딩 반경 × 4 | 거부 |
  | 파생 상태(위치·속도·임펄스·PCM) | `MAX_STATE` 1e15 | 포화 + `StateOverflow` |
  | 브로드페이즈 페어 | `max_pairs_per_body × 바디 수 + 1024`, **바이트 상한으로 재절단** | `ResourceLimit` |
  | 스텝 스크래치 총량 | `MAX_STEP_SCRATCH_BYTES` (128 MiB) | `ResourceLimit` |

  **개수 예산만으로는 부족하다**: 페어 뒤에 constraint·키·HashSet·SoA가 따라붙어 실제
  메모리는 개수의 몇 배가 된다. 총 바이트로 상한을 정하고 그것으로 페어 상한을 되돌려
  계산하므로, 어떤 입력이 와도 한 스텝 스크래치가 상한을 넘지 않는다.
  모든 스텝 컨테이너(페어·lookup·constraint·키·live_keys·SoA·union-find·excluded)는
  **`try_reserve`로 미리 잡는다** — 암묵 재할당은 abort/trap이라 오류 ABI를 깬다.

  페어 예산 기본값(64/바디)의 여유는 실측했다 — 40단 피라미드(820 바디)가 예산의 **8.7%**,
  50단이 8.8%를 쓴다(밀집 스택도 ~11배 여유). `Diagnostics::pairs`/`pair_budget`으로
  호스트가 직접 확인할 수 있다.
  `ResourceLimit`으로 스텝을 포기해도 **커맨드는 이미 적용된 상태**다 — 페어 수는 커맨드
  적용 뒤의 배치에서만 알 수 있기 때문이다. "**커맨드 적용됨, 물리 스텝 건너뜀**"이 계약이며,
  재시도해도 커맨드가 사라지지 않는다(이미 반영됐다). 롤백이 필요하면 호스트가
  `try_snapshot()`으로 스텝 전 상태를 잡아둔다 — 엔진이 매 스텝 스냅샷 비용을 강제하지 않는다.
  플래그는 **매 스텝 초기화**되므로 원인을 없애면 다음 스텝은 정상 성공한다.
- **OOB 바디는 모든 시뮬레이션 경로에서 빠진다** — 브로드페이즈에 static anchor로 들어가고
  중력·속도/위치 적분·조인트·슬립 판정에서 제외된다. 다른 바디는 여전히 부딪힐 수 있지만
  자신은 움직이지 않는다.

  **앵커가 바디별로도 묶이는 이유**: 전역 상한만 두면 반지름 1mm 구에 1000m 앵커를 붙일 수
  있고, K 행렬의 고유 스케일이 2.4e4 : 6e16이 되어 상대 det가 임계 아래로 떨어져
  `Mat3::inverse`가 0 행렬을 돌려준다 — 조인트가 **오류 없이 조용히 풀린다**.
  레버암을 바디 크기에 묶으면 `r²·I⁻¹`이 `m⁻¹`과 같은 자릿수에 남아 조건수가
  형상 스케일과 무관해진다.

  **앵커가 셰이프 범위인 이유**: 앵커는 레버암이고 점 속도는 `v + ω×r`다. 앵커를 월드
  범위까지 허용하면 각속도 100 rad/s × 앵커 1e4 m = 점 속도 1e6 m/s가 되어 임펄스 논증이
  깨진다. **월드 범위가 1e4인 이유**: 1e4 부근의 f32 간격(≈9.8e-4 m)이
  `MIN_SHAPE_EXTENT`(1mm) 이하여야 작은 물체가 좌표 반올림으로 퇴화하지 않는다.
  더 넓은 월드는 floating-origin(주기적 rebase)이 필요하며 v1의 계약이 아니다.
- **월드 범위 이탈은 정의된 정책이다**: 적분으로 위치가 `MAX_INPUT`을 벗어나면 경계에
  고정하고 속도를 0으로 만든 뒤 **시뮬레이션에서 제외**한다(`is_out_of_bounds`,
  `Diagnostics::out_of_bounds`). 이는 sleep과 **다른 상태**다 — sleep으로 처리하면
  조인트로 연결된 상대가 깨어 있을 때 wake 폐쇄가 매 프레임 되살려
  이동→고정→sleep→wake를 반복한다. 해제는 호스트가 `set_pose`로 월드 안에
  되돌리는 경로뿐이다(자동 복귀 없음).
  10km 밖에서는 f32 간격이 최소 특징 크기를 넘어 충돌 판정이 의미를 잃으므로,
  조용히 계속 계산하는 것이 가장 나쁜 선택이다.
- **리더는 라이브 API와 같은 validator를 호출한다**(`Body::validate`/`Joint::validate`).
  필드마다 범위 검사를 따로 적으면 새 차원을 도입할 때마다 한쪽만 고쳐 비대칭이
  재생산된다 — 실제로 네 번 재발했다.
- **`WorldParams`는 캐노니컬 상태**다(스냅샷 v4에 포함). 미래 동작을 바꾸는 mutable
  state이므로, 빠지면 같은 스냅샷을 복원한 두 월드의 해시는 같은데 다음 스텝부터 갈린다.
- hull은 **회전 불변** 최소 두께를 요구한다. 축 정렬 span만 보면 한 평면 위의 점들이
  통과해 저차원 polytope가 GJK/EPA로 들어간다.
- **속도 상한은 물리 파라미터다** (`WorldParams::max_linear_velocity` 500 m/s,
  `max_angular_velocity` 100 rad/s — Jolt `mMaxLinearVelocity` 계열). 터널링·폭주를 막는
  정상 기능이며 도달은 오류가 아니라 `Diagnostics::velocity_clamped`로 집계된다.
  **이것이 파생 상태를 유계로 만들어 정책이 step에 대해 닫힌다** — 겹친 바디를 밀어내는
  정상 물리도 상한을 향해 가속하므로, 속도가 유계라야 임펄스와 변위가 유계가 된다.
- `MAX_STATE` 도달은 **정상 물리에서 일어나지 않는다**(지원 범위 안 최악 임펄스 ≈ 2e13,
  상한은 그 50배 위). 도달하면 지원 범위 밖 입력이거나 엔진 버그이므로 상태를 안전하게
  포화시키되 `try_step`이 `StateOverflow`를 반환하고 `Diagnostics::state_saturations`에
  집계한다 — 조용히 삼키지 않는다.
- 공개 커맨드 스키마(`Command`)에 **바디 추가가 없다**. 슬롯 예약과 커맨드 등록이 한 원자
  연산이어야 하므로 정본 경로는 `enqueue_add_body`(예약 핸들을 즉시 반환)뿐이다.
- hull은 정점 `MAX_HULL_POINTS`(**32**)까지 — 최소 폭을 삼중조합 전수로 **정확히** 검증할 수 있는 범위다.
  더 복잡한 메시는 convex decomposition으로 여러 hull로 나눈다(검증할 수 없는 것을 지원한다고 말하지 않는다).

- **CCD 없음 (v1).** 브로드페이즈는 `velocity × dt`로 sweep AABB를 확장하지만
  내로우페이즈는 **현재 자세에서만** 판정한다. 500 m/s 물체는 60Hz에 8.3 m를 지나므로
  얇은 벽을 한 프레임에 통과할 수 있다. 호스트가 `max_linear_velocity`를 낮추거나
  `substeps`를 올려 `속도 × dt / substeps < 최소 두께`를 유지해야 한다.
  swept 내로우페이즈는 설계 §4.5의 M4 과제다.

## 규율 (설계 문서에서 상속)

- FMA 비의존(relaxed-simd는 추후 별도 feature) · 재결합 금지(기본 프로파일 유지)
- SIMD 강등은 벤치 배너에 `simd-OFF`로 표시 — 조용한 폴백 금지(설계 §6)
- **wasm 타깃은 `#[should_panic]` 테스트를 실행하지 않는다**(unwinding 미지원 → ignored).
  경계 거부 테스트의 실제 커버리지는 네이티브 레그에서만 나온다 — wasm 녹색 수치를
  전체 커버리지로 읽지 말 것.
- 벤치는 체크섬을 함께 출력 — 같은 타깃·빌드에서 체크섬 불일치 = L0 결정론 위반 신호(설계 §8)
